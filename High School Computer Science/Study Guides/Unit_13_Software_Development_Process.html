Software Development Process软件开发流程

Professional software is not written in one burst of inspiration; it is built through a disciplined life cycle (SDLC) that transforms a vague wish into a working, documented, maintainable product. This guide walks every phase from requirements gathering through design, implementation, testing, documentation, and maintenance, then introduces the collaboration tools, version control (Git) and code review, that make team software development work. Pseudocode and flowcharts appear in the design section; code examples are in Python but the concepts apply to any language.专业软件不是灵感爆发的产物，而是通过严格的生命周期（SDLC，软件开发生命周期）将模糊的需求（requirements，需求）转化为可工作、有文档、可维护产品的结果。本指南逐一讲解需求收集、设计（design，设计）、实现（implementation，实现）、测试（testing，测试）、文档（documentation，文档）和维护（maintenance，维护）各阶段，再介绍版本控制（version control，版本控制，Git）和代码审查等协作工具。设计节包含伪代码和流程图；代码示例用 Python，但概念适用于任何语言。

The seven SDLC phases: memorise these in order.七个 SDLC 阶段：按顺序背熟。
  • 1. Problem definition / Requirements1. 问题定义 / 需求: what does the software need to do? Collect user needs, constraints, and success criteria.：软件需要做什么？收集用户需求、约束条件和成功标准。
  • 2. Analysis2. 分析: study the requirements in detail; identify inputs, outputs, data flows, and edge cases.：详细研究需求；确定输入、输出、数据流和边缘情况。
  • 3. Design3. 设计: produce design artifacts: flowcharts, pseudocode, UML diagrams, data structures, user interface sketches.：产出设计制品：流程图、伪代码、UML 图、数据结构、用户界面草图。
  • 4. Implementation (coding)4. 实现（编码）: translate the design into working code following coding standards.：按照编码规范将设计转化为可运行的代码。
  • 5. Testing5. 测试: verify the code works correctly using a formal test plan (normal, boundary, and error cases).：使用正式测试计划（正常、边界和错误情况）验证代码是否正确运行。
  • 6. Documentation / Deployment6. 文档 / 部署: write user and technical documentation; release the software to users.：编写用户文档和技术文档；将软件发布给用户。
  • 7. Maintenance7. 维护: fix bugs that appear after release, add new features, and adapt the software as requirements change.：修复发布后出现的错误，添加新功能，并随着需求变化调整软件。
Waterfall vs Agile: the waterfall model runs the seven phases in strict sequence (plan everything before coding). Agile iterates in short sprints, revisiting requirements → design → code → test in quick cycles. Ontario ICS3U B4.1 names the phases explicitly; CSTA 3B-AP-17 says "processes could include agile, spiral, or waterfall."瀑布模型与敏捷：瀑布模型按严格顺序执行七个阶段（在编码前规划好一切）。敏捷以短冲刺迭代，在快速循环中反复经历需求 → 设计 → 编码 → 测试。安大略 ICS3U B4.1 明确命名各阶段；CSTA 3B-AP-17 说"过程可包括敏捷、螺旋或瀑布"。

Two phase lists, one process两份阶段列表，同一个过程

Sources word the phases a little differently, so match them by meaning, not by name. This guide puts coding under Implementation and release under Documentation / Deployment. Ontario ICS3U B4.1 lists problem definition, analysis, design, writing code, testing, implementation and maintenance. Its writing code is this guide's Implementation (coding); its implementation, putting the finished program into use, is this guide's Documentation / Deployment. Common error: treating the words as interchangeable. In B4.1, implementation comes after testing.不同资料对阶段的叫法略有差异，所以要按含义而不是按名称来对应。本指南把编码放在“实现”下，把发布放在“文档 / 部署”下。安大略 ICS3U B4.1 列出的是问题定义、分析、设计、编写代码、测试、实现和维护。它的编写代码对应本指南的“实现（编码）”；它的实现（把完成的程序投入使用）对应本指南的“文档 / 部署”。常见错误：把这些词当作可以互换。在 B4.1 中，实现排在测试之后。

Worked Example 1: Mapping a homework tracker through the SDLC例题 1：作业追踪应用的 SDLC 阶段分析

Problem: a student team is tasked with building a homework-tracker app. Walk each SDLC phase for this project.问题：一个学生团队负责构建一个作业追踪应用。逐一分析该项目的每个 SDLC 阶段。

Requirements.需求。 Users (students) need to add tasks with due dates, mark tasks complete, and sort by urgency. Constraint: must work on mobile.用户（学生）需要添加带截止日期的任务、标记任务为已完成并按紧迫性排序。约束：必须在手机上运行。

Analysis.分析。 Inputs: task name, subject, due date. Outputs: sorted task list. Data: each task stores {name, subject, due_date, done}. Edge case: two tasks on the same due date.输入：任务名称、学科、截止日期。输出：已排序的任务列表。数据：每个任务存储 {name, subject, due_date, done}。边缘情况：两个任务的截止日期相同。

Design.设计。 Produce a flowchart for "add task," pseudocode for "sort by due date," and a simple UML class sketch showing Task attributes and methods.为"添加任务"画流程图，为"按截止日期排序"写伪代码，并画出显示 Task 属性和方法的简单 UML 类草图。

Implementation.实现。 Write Python/JavaScript code following the design. Apply coding standards: meaningful names, inline comments, no magic numbers.按照设计编写 Python/JavaScript 代码。遵循编码规范：有意义的命名、内联注释、无魔法数字。

Testing.测试。 Test plan: normal case (add 3 tasks, verify sort), boundary case (task due today), error case (no tasks in list: display "no tasks").测试计划：正常情况（添加 3 个任务，验证排序），边界情况（今天截止的任务），错误情况（列表中无任务：显示"无任务"）。

Documentation/Deployment.文档/部署。 Write a README describing how to install and use the app. Deploy to the school server.编写描述如何安装和使用应用的 README。部署到学校服务器。

Maintenance.维护。 Users report that tasks with the same due date display in the wrong order; fix the sort comparator and increment the version number.用户报告截止日期相同的任务显示顺序不正确；修复排序比较器并更新版本号。

Worked Example 2: Comparing a waterfall plan and an agile plan例题 2：比较瀑布计划与敏捷计划

Problem: the homework-tracker team has 16 weeks and 8 features to build. Plan A (waterfall): Requirements 2 weeks, Design 3, Implementation 6, Testing 3, Release 2. Plan B (agile): eight 2-week sprints, each building, testing and releasing one feature. (a) When do users first get working software in each plan? (b) How many releases happen by the end of week 16? (c) In week 8 users ask for a change to feature 5. Which plan absorbs it more cheaply, and why?问题：作业追踪应用的团队有 16 周时间，要完成 8 个功能。方案 A（瀑布）：需求 2 周、设计 3 周、实现 6 周、测试 3 周、发布 2 周。方案 B（敏捷）：8 个 2 周的冲刺，每个冲刺构建、测试并发布一个功能。(a) 两种方案中用户分别在何时第一次得到可用软件？(b) 到第 16 周结束共有几次发布？(c) 第 8 周用户要求修改功能 5。哪种方案处理起来代价更低，为什么？

Plan A (waterfall).方案 A（瀑布）。 Phases run one after another: Requirements 2 weeks, Design 3, Implementation 6, Testing 3, Release 2. The code below adds them up to find when users first get working software.各阶段依次进行：需求 2 周、设计 3 周、实现 6 周、测试 3 周、发布 2 周。下面的代码把它们加起来，求出用户第一次拿到可用软件的时间。

phases = {"Requirements": 2, "Design": 3, "Implementation": 6, "Testing": 3, "Release": 2}
week = 0
for name, weeks in phases.items():
    week += weeks
    print(f"{name:<15} ends week {week}")
print("Waterfall: first working release at week", week)

SPRINT_WEEKS = 2
SPRINTS = 8
releases = [SPRINT_WEEKS * n for n in range(1, SPRINTS + 1)]
print("Agile releases at weeks", releases)

Output:输出：

Requirements    ends week 2
Design          ends week 5
Implementation  ends week 11
Testing         ends week 14
Release         ends week 16
Waterfall: first working release at week 16
Agile releases at weeks [2, 4, 6, 8, 10, 12, 14, 16]

(a) First working software.(a) 第一次得到可用软件。 Waterfall: week 16, because nothing is released until Testing and Release are finished. Agile: week 2, because sprint 1 already ends with a working (small) version.瀑布：第 16 周，因为测试和发布完成之前什么都不会发布。敏捷：第 2 周，因为第 1 个冲刺结束时就已经有一个可用的（小）版本。

(b) Releases.(b) 发布次数。 Waterfall: 1 release (week 16). Agile: 8 releases (weeks 2, 4, 6, 8, 10, 12, 14, 16).瀑布：1 次发布（第 16 周）。敏捷：8 次发布（第 2、4、6、8、10、12、14、16 周）。

(c) The change request in week 8.(c) 第 8 周的变更请求。 Waterfall: the requirements were fixed in weeks 0 to 2 and the design in weeks 2 to 5, and implementation (weeks 5 to 11) is half done, so the change means editing the requirements document, the design and code already written, then re-planning the tests. Agile: sprints 1 to 4 have finished feature 4, and feature 5 has not been started, so the change is made to the backlog (the list of work still to do) before any code for feature 5 exists.瀑布：需求在第 0 到 2 周定稿，设计在第 2 到 5 周定稿，实现（第 5 到 11 周）已完成一半，所以这个变更意味着要修改需求文档、设计和已写好的代码，再重新规划测试。敏捷：冲刺 1 到 4 已完成功能 4，功能 5 还没开始，所以变更只需在待办列表（backlog，尚未完成的工作清单）中修改，此时功能 5 的代码还不存在。

Why this works.为什么这样可行。 Agile shortens the feedback loop (the time between a decision and a user's reaction to it) from 16 weeks to 2. The price is the tradeoff in the cram box: frequent releases need constant communication with users. A real agile sprint still contains a small requirements, design, code and test cycle, so the phases do not disappear. The numbers are a teaching model, not a measurement of any real team.敏捷把反馈回路（从做出决定到用户作出反应之间的时间）从 16 周缩短到 2 周。代价就是速记框里的权衡：频繁发布需要与用户持续沟通。真实的敏捷冲刺内部仍然包含一个小型的需求、设计、编码和测试循环，所以阶段并没有消失。这些数字只是教学模型，并不是对任何真实团队的测量。

Command words: state the seven phases in order; identify the phase an activity belongs to; compare two models by giving a point for each on the same dimension (for example, when users first see working software, or what a late change costs); justify a choice by tying it to the project. Going deeper: agile vs waterfall vs spiral深入：敏捷与瀑布与螺旋模型

CSTA 3B-AP-17 (verbatim): "Plan and develop programs for broad audiences using a software life cycle process. Processes could include agile, spiral, or waterfall." The three models differ in how rigidly they enforce phase order. Waterfall: each phase finishes completely before the next begins; changes are expensive. Agile: short sprints (commonly one to four weeks; this guide uses two), each delivering a working increment; requirements can change between sprints. Spiral: each revolution of the spiral adds risk analysis before the next round of design/build/test. Ontario ICS4U strand B asks students to manage a student team project and names tools such as a Gantt chart, PERT chart or calendar (B1.4); a team may plan that work with sprints or with a Gantt chart. A useful target is to describe each model and name a tradeoff (waterfall: predictable but inflexible; agile: flexible but requires constant communication).CSTA 3B-AP-17（原文）："使用软件生命周期流程为广大受众规划和开发程序。流程可包括敏捷、螺旋或瀑布。"三种模型的区别在于阶段顺序的严格程度。瀑布：每个阶段完全完成后才开始下一个；变更代价高昂。敏捷：短冲刺（通常一到四周；本指南用两周），每次交付一个可运行的增量；需求可在冲刺之间变化。螺旋：每圈螺旋在下一轮设计/构建/测试之前增加风险分析。安大略 ICS4U B 单元要求学生管理学生团队项目，并列出甘特图、PERT 图或日历等工具（B1.4）；团队可以用冲刺或甘特图来规划这项工作。一个有用的目标是能够描述每种模型并指出一个权衡（瀑布：可预测但不灵活；敏捷：灵活但需要持续沟通）。

Section 2 · Requirements and planning第 2 节 · 需求与规划

Requirements and Planning需求与规划

Learning objectives学习目标
  • Classify a requirement as functional or non-functional and give the reason.
  • Rewrite a vague requirement so that it is specific, numbered and testable.
  • Write a user story with acceptance criteria in Given/When/Then form.
  • Find the project length, the critical path and the slack of each task from a list of durations and dependencies.
  • Turn a backlog size and a team velocity into a number of sprints.
  • 对需求进行功能性或非功能性分类，并说明理由。
  • 把含糊的需求改写成具体、有编号、可测试的需求。
  • 用“给定 / 当 / 则”（Given/When/Then）形式写出带验收标准的用户故事。
  • 根据任务工期和依赖关系，求出项目总长度、关键路径和每个任务的余量。

Planning: tasks, dependencies and the critical path规划：任务、依赖和关键路径

A plan splits the project into tasks, each with a duration, and records which tasks must finish before another can start (its dependencies). A task can start when its slowest prerequisite finishes. The critical path is the longest chain of dependent tasks; its total is the shortest possible project length, because those tasks cannot overlap. Slack is how long a task can be delayed without delaying the project; tasks on the critical path have slack 0. A Gantt chart draws each task as a bar on a time axis. Ontario ICS4U B1.4 names a Gantt chart or PERT chart as a project-management tool. In a sprint-based plan the team instead measures its velocity, the story points it finishes per sprint, and divides the remaining backlog by it.计划把项目拆分为任务（task），每个任务有工期，并记录哪些任务必须先完成才能开始另一个任务（即它的依赖，dependency）。一个任务在它最慢的前置任务完成后才能开始。关键路径（critical path）是相互依赖的任务中最长的一条链；它的总和就是项目最短可能的长度，因为这些任务无法重叠。余量（slack）是任务可以延误而不拖延项目的时间；关键路径上的任务余量为 0。甘特图（Gantt chart）把每个任务画成时间轴上的一根条。安大略 ICS4U B1.4 把甘特图或 PERT 图列为项目管理工具。在以冲刺为单位的计划中，团队改为衡量自己的速度（velocity，每个冲刺完成的故事点数），再用它去除剩余的待办列表。

The code does a forward pass (earliest start and finish: a task starts when its slowest prerequisite finishes) and then a backward pass (the latest each task may finish without delaying the project).代码先做前向推算（最早开始和结束：任务在最慢的前置任务结束后才开始），再做后向推算（每个任务在不拖延项目的前提下最晚可以何时结束）。

tasks = {
    "A": (3, []),          # write requirements
    "B": (4, ["A"]),       # design screens
    "C": (2, ["A"]),       # design data model
    "D": (6, ["B"]),       # code screens

    "G": (3, ["C"]),       # write test plan
    "H": (3, ["F", "G"]),  # run tests
    "I": (2, ["F"]),       # write user guide
    "J": (1, ["H", "I"]),  # release
}

# forward pass: a task starts when its slowest prerequisite finishes
start, finish = {}, {}
for name, (days, needs) in tasks.items():   # every prerequisite is listed first
    start[name] = max((finish[n] for n in needs), default=0)
    finish[name] = start[name] + days
project_days = max(finish.values())
print("Project length:", project_days, "days")

# backward pass: the latest each task may finish without delaying the project
latest_finish = {name: project_days for name in tasks}
for name in reversed(list(tasks)):
    days, needs = tasks[name]
    for n in needs:
        latest_finish[n] = min(latest_finish[n], latest_finish[name] - days)

for name in tasks:
    slack = latest_finish[name] - finish[name]
    note = "  <- critical" if slack == 0 else ""
    print(f"{name}: day {start[name]:>2} to {finish[name]:>2}, slack {slack}{note}")

Common Questions常见问题

What are the stages of the software development life cycle?软件开发生命周期有哪些阶段？

The SDLC moves through analysing requirements, designing the solution with artifacts like flowcharts and pseudocode, implementing the code to coding standards, testing with a formal plan, documenting, and finally maintenance to fix bugs and add features after release.软件开发生命周期依次经过分析需求、用流程图和伪代码等成果设计方案、按编码规范实现代码、按正式计划测试、编写文档，最后是发布后修复漏洞和增加功能的维护阶段。

What makes a good software requirement?什么样的软件需求才算好？

A good requirement is specific and measurable enough to write a test case for, with a concrete action and a measurable outcome. Vague phrases like user-friendly, clean code, or fast database are not requirements because they cannot be tested.好的需求足够具体且可衡量，能为它写出测试用例，包含明确的动作和可衡量的结果。像用户友好、代码整洁或数据库快速这类含糊的说法不算需求，因为它们无法测试。
